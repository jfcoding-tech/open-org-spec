# Owner-health

A tool of the open-org-spec observability capability. Aggregates the role-header information scattered across a conformant repository into one indexed view: who holds which role at which scope, sortable per-person (span) and per-scope (bus factor).

**Status:** Draft (0.1.0)
**Type:** Command
**Reference implementation:** an adopter executes the base spec via a relay at their command directory (e.g. `.claude/commands/owner-health.md`), extended at `.open-org-spec/extensions/observability/owner-health/spec.md`.

## Purpose

A conformant repository names people in role headers throughout its specs — `Owner: …`, `Lead: …`, `Approver: …` — but the *aggregate* picture of who holds how many roles is invisible from any one file. Two questions cannot be answered without walking the entire repo: *is anyone overloaded?* and *which scopes have a bus factor of one?*

This tool answers both. It walks the repo, collects every role header, cross-references against any active `people.md` rosters, and writes a single markdown index — sorted two ways — to a path the adopter declares. The index serves both Claude users (who invoke the command and get a fresh digest) and humans reading the repo without Claude (who open the cached file).

## Pattern

### Inputs

- **Role-header set** — the universal set is `Owner`, `Lead`, `Driver`, `Approver` (from the [`people-at-scope`](../../people/spec.md) function vocabulary). The adopter's [`observability/spec.md`](../spec.md) extension adds more.
- **Scope tree** — the list of top-level folders to walk, declared by the adopter's capability extension.
- **People resolution mode** — when the [`people-at-scope`](../../people/spec.md) capability is active, the tool cross-references `people.md` files at each scope for canonical names; otherwise it uses the header text verbatim.
- **Output path** — declared by the adopter's capability extension.

### Step 1 — Walk the scope tree

For each top-level folder declared by the adopter, walk recursively. At each markdown file encountered, scan for lines matching the role-header pattern: a line beginning with the role name followed by a colon, with optional bold/markdown formatting.

The standard pattern: `**<RoleName>:** <person identifier>` or `- **<RoleName>:** <person identifier>` or `<RoleName>: <person identifier>` (variations are common; the tool spec describes the regex shape, the implementation handles them).

The tool also reads `people.md` files when present. Per the [`people-at-scope`](../../people/spec.md) capability, the **Function** column of the working group table is a role declaration; the **Lead table** is a role declaration of `Lead` at that scope.

### Step 2 — Cross-reference (optional)

If the [`people-at-scope`](../../people/spec.md) capability is active in the adopter's manifest, look up each named person in the nearest `people.md` for canonical full-name and affiliation. This catches variations (a short name vs the canonical full name) and surfaces the person's organisational home alongside the role.

If the capability is not active, skip this step — the tool degrades gracefully, using header text verbatim.

### Step 3 — Aggregate

Build two pivots from the collected (person, role, scope, source-file) tuples:

- **Per-person.** For each unique person, list every (role, scope, source-file) row. Sort persons by descending row count (most roles first).
- **Per-scope.** For each scope folder, list every (role, person, source-file) row. Sort scopes by ascending unique-person count (fewest first — bus-factor-of-one surfaces at the top).

### Step 4 — Render

Write a markdown file at the output path declared by the adopter's extension. The output file must begin with a machine-readable YAML front-matter block containing these key metrics, followed by the prose body.

```yaml
key_metrics:
  ownership_coverage_pct: N.N
  bus_factor_warnings: N
  unresolved_owners: N
```

The structure:

1. **Generation header** — single line: *"Generated by `/owner-health` on YYYY-MM-DD HH:MM. Repo HEAD: `<short-sha>`. Re-run the command to refresh."*
2. **Summary block** — total unique people, total role-occurrences, top-N most-loaded people, count of scopes flagged as bus-factor-one.
3. **Per-person section** — one sub-heading per person, listing their roles as a table.
4. **Per-scope section** — one sub-heading per scope folder, listing the people who hold roles there.

The adopter's tool extension may add or override section content (e.g. include a mermaid diagram, add additional columns, change sort orders).

### Step 5 — Return digest

In addition to writing the file, return a short digest to the invoking interface:

- Total people and total role-occurrences.
- The single most-loaded person (name + count).
- Up to 3 scopes flagged as bus-factor-one.
- A link to the generated file for the full view.

The file is the durable artefact; the digest is the conversation-time response.

### Extension points

- **Additional role headers** — adopters add their own role markers.
- **Scope-tree composition** — which folders count as scopes worth walking, and any to exclude (e.g. archived projects).
- **Threshold values** — what counts as "most-loaded" (top-N), what counts as bus-factor-warning (single-Owner scopes, single-Owner-with-no-Approver scopes, etc.).
- **Renderer specifics** — additional sections (mermaid diagrams, role-mix charts), column overrides, alternate sort orders.
- **People resolution behaviour** — whether to skip people whose `people.md` row lists them as `Contributor` or `Member` (broad-role-only mode), or to include every named occurrence.
- **Filename for the cached output** — defaults to `owner-health.md` under the adopter's observability folder.

## What is not prescribed

- **The specific regex for role-header detection.** The pattern is described semantically (line begins with role name + colon); the implementation chooses the exact form to match the markdown conventions in the adopter's repo.
- **Whether scopes with zero people are surfaced.** Adopter-specific — some want empty scopes flagged, others want them hidden.
- **The bus-factor threshold formula.** "One Owner and no Co-steward / Approver" is one definition; adopters may define their own and declare it in the extension.

## Rationale

Of the six metric families named in the observability capability, people involvement is the smallest scan with the highest signal-per-line-of-spec-walked. Role headers are short, structured, and tightly conventionalised — a clean first instance of the capability that lets adopters validate the cached-output convention, the extension-point shape, and the digest format before more elaborate metric families (decision health, spec health) earn their own tools.

The dual pivot (per-person *and* per-scope) is the design crux. A per-person view answers "who is overloaded"; a per-scope view answers "where is fragile." Two questions, two views, one scan.

## Adoption

Adopters activate `owner-health` by:

1. Declaring `capabilities.observability.tool_extensions.owner-health` in their manifest, pointing at `.open-org-spec/extensions/observability/owner-health/spec.md`.
2. Writing the tool extension with adopter-specific defaults (additional role headers if any, scope-tree specifics, threshold values, renderer overrides).
3. Wiring a relay at their LLM interface's command directory (e.g. `.claude/commands/owner-health.md`) pointing to this spec.

Worked example: an adopter wires a relay at their command directory (e.g. `.claude/commands/owner-health.md`), an extension at `.open-org-spec/extensions/observability/owner-health/spec.md`, declared in `.open-org-spec/config.yaml`.
