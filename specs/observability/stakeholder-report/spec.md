# Stakeholder Report

**Owner:** Javier Fernandez
**Status:** Active

A self-contained HTML report generated from the observability suite's outputs. Designed for stakeholders who do not have access to the repository — translates governance health metrics into plain language that answers "is the organisation governing itself well?"

Distinct from [`../dashboard.md`](../dashboard.md) (the technical Claude Code companion for practitioners) and [`../suite.md`](../suite.md) (the scheduled execution pattern). This report is the **stakeholder-facing output** — a rendered artefact, not an interactive tool.

---

## Purpose

Governance tooling produces signal. Stakeholders need interpretation. The stakeholder report bridges the two: it reads from the same generated outputs as the technical dashboard but frames every metric in terms of accountability, velocity, and responsiveness — the governance properties that matter to executives and cross-functional leads.

The report is intentionally non-technical. It never mentions specs, submodules, or LLM invocations.

---

## Output

A single self-contained `.html` file. Requirements:

- **No external dependencies.** All CSS, JavaScript, and chart libraries are embedded inline. The file opens in any browser without an internet connection.
- **Printable.** Print-friendly stylesheet included. Stakeholders can produce a PDF from the browser.
- **Dated and versioned.** Footer shows generation date, the period covered, and the repo HEAD SHA.
- **Shareable.** The file can be emailed or shared via Drive without requiring repo access.

The adopter declares the output path in their extension. Convention: `governance/observability/stakeholder-report.html`.

---

## Audience framing

Every metric section is written for someone who asks "is the organisation working well?" — not "is the repo conformant?". The report avoids jargon by mapping technical observations to business language:

| Technical | Stakeholder language |
|---|---|
| Specs with named Owner | Accountability coverage |
| Open decisions > N days | Blocked decisions |
| Time to `decided_at` | Decision velocity |
| Feedback entries unresolved | Open items waiting for a response |
| Time to `[resolved]` | Responsiveness |
| Active contributors | Team engagement |
| Specs not touched in 90 days | Stale or abandoned work |

## Metrics

### 1. Decision velocity

Sources: decision records (`decisions/` folders, all governed scopes), `decided_at` field.

| Metric | How computed |
|---|---|
| Open decisions | Count of decisions where `Status` is in the open vocabulary |
| Avg time open | For open decisions: today minus filename date |
| Blocked decisions | Open decisions older than adopter-declared stale threshold |
| Recently closed | Decisions with `decided_at` in the last 30 days |
| Avg time to decision | Mean of `(decided_at − filename date)` for decisions closed in the last 90 days |

Display: headline numbers + trend bar (last 4 weeks of closure count). Flag blocked decisions by name and age.

### 2. Accountability coverage

Source: adopter-declared catalogue file.

| Metric | How computed |
|---|---|
| Ownership coverage | % of specs with a non-empty `Owner` field |
| Fully governed scopes | Scopes where all specs have Owner + Status populated |
| Uncovered scopes | Scopes with < adopter-declared threshold % ownership |

Display: percentage with RAG indicator. Per-scope breakdown as a sortable table (lowest coverage first).

### 3. Feedback responsiveness

Sources: `<scope>/feedback.md` files across all governed scopes.

| Metric | How computed |
|---|---|
| Open items | Feedback entries without `[resolved]` marker |
| Avg time to resolution | Mean of `(resolved date − entry date)` for entries resolved in the last 90 days. Entry date from heading (`## YYYY-MM-DD`); resolved date from `[resolved YYYY-MM-DD]` marker. |
| Response rate (30 days) | Entries resolved in last 30 days ÷ entries opened in same period |
| Oldest open item | Entry heading date of the oldest unresolved entry |

Display: headline response rate + oldest open item flagged. Table of open items by scope, sorted by age.

### 4. Contributor engagement

Sources: adopter-declared contributor usage file (generated by the `agent-metrics` agent) and `contributor-activity` output.

| Metric | How computed |
|---|---|
| Active contributors (maps to `git_active_contributors` from contributor-activity; `claude_active_users` from agent-metrics/contributor-usage) | Contributors with ≥ 1 commit (git) or ≥ 1 command run (agent-metrics) in the period |
| Session-only | Contributors who opened sessions but ran no commands (maps to `claude_session_only_users` from agent-metrics/contributor-usage) |
| Inactive | Contributors with no activity (maps to `claude_inactive_users` from agent-metrics/contributor-usage) |
| Engagement rate | Active ÷ (Active + Session-only + Inactive) |

Display: three-bucket donut chart. Trend line over last 4 weeks.

### 5. Collective ownership

Source: adopter-declared spec-activity output file.

| Metric | How computed |
|---|---|
| Lived-in | Specs touched by ≥ 2 distinct authors in last 90 days |
| Stable | Specs touched by 1 author only in last 90 days |
| Untouched | Specs with no activity in last 90 days but opened recently |
| Abandoned | Specs with no activity for > 90 days |
| Collective ownership (`collective_ownership_pct`) | (Lived-in + Stable) ÷ total |

Display: stacked bar by scope. Flag abandoned specs by name.

### 6. Risk health

Source: adopter-declared risk registry file (`governance/risk-registry.yaml` or `governance/catalogue/risks.yaml`).

| Metric | How computed |
|---|---|
| Open risks | Count of risks where `status: open` |
| RED risks | Open risks where RAG is derived as RED (past escalation threshold) |
| AMBER risks | Open risks where RAG is derived as AMBER (approaching threshold) |
| Unowned risks | Risks where `owner` is empty or unresolvable |
| Risks awaiting disposition | Open risks with `disposition_at` older than 14 days |

Display: headline counts with RAG traffic lights. Table of RED risks by scope and owner. Flag unowned risks.

## Extension points

| Extension point | Description | Default |
|---|---|---|
| Output path | Where to write the HTML file | *(required)* |
| Period | Rolling window for trend metrics | 30 days |
| Stale decision threshold | Days before an open decision is flagged | 14 days |
| Ownership coverage threshold | % below which a scope is flagged | 80% |
| Feedback sources | `<scope>/feedback.md` paths to scan | *(required)* |
| Catalogue path | Spec catalogue for ownership metrics | *(required)* |
| Contributor usage path | Generated contributor usage file | *(required)* |
| Spec-activity path | Generated spec-activity output | *(required)* |
| Decision folder paths | Where to walk for decision records | *(required)* |
| Organisation name | Shown in the report header | *(required)* |
| Report title | H1 of the generated HTML | `Organisation Governance Health` |
| `risk_registry_path` | Path to the risk registry file | *(required when `risk-at-scope` is active)* |

---

## Implementation pattern

The report is generated by an automated agent step that:

1. Reads all extension-point-declared input files (catalogue, contributor usage, spec-activity output, feedback inboxes, decision records)
2. Computes the six metric groups
3. Renders a self-contained HTML file with embedded CSS and chart library (Chart.js or equivalent, embedded inline)
4. Writes to the declared output path and commits alongside the other suite outputs

The agent step runs **after** all five observability tools have completed in the suite run — it reads their outputs, not the raw repo.

For the chart library: embed the minified source inline in a `<script>` tag. No CDN. No runtime HTTP requests.
