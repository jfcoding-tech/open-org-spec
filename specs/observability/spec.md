# Observability

A capability of open-org-spec describing how a conformant repository exposes its own state to the contributors and adopters who maintain it — what gets measured, where the measurements live, and how an adopter publishes views over them.

**Status:** Draft (0.1.0)

## Purpose

A spec-driven repository accumulates structure — scopes with role headers, decision folders, project lifecycle markers, feedback inboxes, ownership declarations. The structure is legible to a human reading any one file, but the *aggregate* picture (who owns how many things, how many decisions are open, which specs have gone stale, which projects are past close) is not surfaced unless someone walks the repo manually.

This capability codifies the recurring pattern so adopters do not re-derive metric families, walking conventions, or output conventions every time someone wants to ask "who is overloaded?" or "what decisions have been open for too long?"

The thesis is that the repo's own conventions are tight enough to aggregate without extra convention pressure. The capability validates that thesis by codifying which conventions get scanned and what shape the output takes.

## Pattern

### What observability is

**Observability** is any artefact that *reports on* a conformant repository's state by reading the conventions other capabilities have established. A workflow spec describes what a cluster does; a generated index that lists every scope's Owner is observability.

Observability is distinct from `tooling` — tooling is *how* a command is wired (slash command, agent, hook, script); observability is *what* gets measured and rendered. A specific tool that reports observability data (`/owner-health`, `/decision-health`) is a tool of the tooling capability whose content is an observability tool's spec. The capability split is intentional: a future adopter might surface observability through a non-tooling interface (a generated webpage, a static-site dashboard) without rewriting what is measured.

### Metric families

A conformant repo can be observed through the following families. Each family corresponds to specs and headers that other open-org-spec capabilities already require.

- **People involvement** — derived from role headers (`Owner`, `Lead`, `Driver`, `Approver`) and `people.md` rosters. Surfaces span (how many scopes a person appears in), role mix, bus factor (scopes with one Owner and no co-authority), and inbox load (open `→ <name>` feedback entries).
- **Decision flow** — derived from `decisions/` folders at each scope. Surfaces count per scope, open vs resolved ratio, time-to-decision (proposed → decided), decision-authority distribution.
- **Spec health** — derived from spec headers (`Status`, last-modified, cross-reference links). Surfaces specs in Draft for too long, specs unedited for too long, specs without an Owner, broken relative links.
- **Project lifecycle** — derived from project spec headers (`Status`, `Started`, `Target close`, `Outcome`, `Hypothesis validation`). Surfaces active vs closed, projects past target close with no status update, hypothesis-validation rate at close.
- **Cross-flow** — derived from cross-references and `feedback.md` files. Surfaces feedback inbox aging, capabilities graduated from projects, decisions cited from other scopes.
- **Adoption** — derived from adopter manifests (`.open-org-spec/config.yaml` per adopter). Surfaces which capabilities each adopter has activated, which extension points each adopter has filled in, drift between the standard's current spec and an adopter's frozen `standard_version`.

The families are reference points, not a closed set. New families that earn their place by being broadly useful are added by revision to this capability. Tools graduate one family at a time — `/owner-health` is the first instance of people involvement; later tools cover the others.

### Shape of an observability tool

Every tool of this capability follows the same shape:

1. **Pull-based.** The tool is invoked on demand. It does not run on a schedule, modify other specs, or block PR-time operations (those are layer-2 concerns; see "What is not prescribed").
2. **Reads the live repo.** No persistent state beyond the repo itself. Every invocation re-scans; there is no cache to maintain or invalidate.
3. **Writes a cached markdown file.** The tool's primary output is a markdown file at a path the adopter declares, generated fresh on every invocation. The file is the artefact — it lives in the repo, is readable on GitHub web or in Obsidian without invoking the tool, and links to it are stable.
4. **Carries a generation header.** The cached file starts with a header line: `*Generated by /<tool-name> on YYYY-MM-DD HH:MM. Repo HEAD: <short-sha>. Re-run the command to refresh.*` The timestamp makes staleness visible; the SHA grounds the output in a specific repo state.
5. **Surfaces results in the invoking interface.** In addition to writing the file, the tool returns a short digest to the caller — the headline numbers, the most surprising rows. The file is for the repo's other readers; the digest is for whoever invoked the command.

### Where outputs live

The cached output of every observability tool lives at a path the adopter declares. The standard names the convention: outputs are co-located in a single observability folder at the adopter's chosen scope (typically `governance/observability/` or equivalent), so a contributor reading the repo finds all observability artefacts in one place.

The adopter's extension declares:
- The base path for generated outputs.
- The filename convention (typically `<tool-name>.md`).
- Whether outputs are committed to the repo (default yes — visibility is the point) or git-ignored.

### Extension points

The capability declares extension points that tools and adopters fill in:

- **Role-header set** — the universal set is `Owner`, `Lead`, `Driver`, `Approver`. Adopters may add additional role headers (e.g. `Co-steward`, `Decision authority`) in their extension. Tools scanning role headers read the merged set.
- **Scope tree** — which top-level folders to walk. The standard names typical scopes (clusters, modules, projects, governance, the standard itself); the adopter's extension lists the exact paths.
- **Threshold values** — bus-factor floor, "stale" age thresholds, inbox-aging thresholds. The standard does not prescribe specific numbers; the adopter declares them in the extension.
- **Output path and naming** — declared per adopter; the standard requires the convention exists, not what it is.
- **Renderer specifics** — whether the generated markdown includes mermaid diagrams, summary blocks, top-N lists. Adopter choice.
- **People resolution** — when a role header names a person, whether to cross-reference an active `people.md` for canonical names and affiliations, or to use the header text verbatim. Available only when [`people-at-scope`](../people/spec.md) is active in the adopter's manifest.

### Ownership

Observability is **infrastructure scope**, like `tooling`. A tool with multiple consumers (any observability index used by contributors across clusters) is governed at infrastructure scope, not within any one consumer's path. The standard's reference adopter places observability under `governance/` to make this explicit.

A tool created by a single team for their own use may start as a project-local artefact and lift to infrastructure scope once a second consumer adopts it. This mirrors the same capability-first principle that applies to `tooling`.

### Lifecycle

1. **Prototype.** A tool is first built as a time-boxed project (`projects/<name>-v0/`). The project validates whether the metric family is worth aggregating — does anyone find the output actionable? does the scan complete reliably? The project has a close criterion; when met, it closes.

2. **Graduation.** A validated prototype graduates to `open-org-spec/specs/observability/<name>/spec.md`. The project closes with a pointer to the spec.

3. **Adoption.** Adopters instantiate the tool by writing an extension at `.open-org-spec/extensions/observability/<name>/spec.md` and a relay at their LLM interface's command directory. The capability extension at `.open-org-spec/extensions/observability/spec.md` carries the adopter-wide observability declarations (base output path, role-header additions, scope tree, thresholds); tool extensions specialise.

4. **Extension.** Adopters may add behaviour not in the generic tool spec. Extensions that prove broadly useful are proposed back to the standard as spec revisions.

## What is not prescribed

- **Push-based observability.** Scheduled jobs, PR-time checks, notification bots, merge blockers. These are layer-2 — they read the same conventions but act on the data. The standard codifies the pull layer first; push behaviours graduate independently once the pull layer is settled.
- **Specific threshold values.** "Stale" is adopter-dependent. The standard names the concept and the extension point; the adopter picks the number.
- **A complete spec per metric family.** This spec names six families. Each family earns its own dedicated tool spec when an instance graduates. People involvement is the first via `owner-health/spec.md`.
- **Whether outputs are committed to git.** The standard recommends committing (visibility is the point) but does not require it. An adopter who prefers git-ignored generation declares so in the extension.
- **Cross-adopter aggregation.** A meta-tool that reads multiple adopters' manifests and reports adoption metrics across them is conceptually part of this capability but lives outside any single adopter's repo. Out of scope for v0.

## Rationale

Observability accumulated in the reference adopter's repo as ad-hoc per-scope commands — `/factory-status` for the AI Factory, `/coach-status` for Phase 2, `/pd-cluster-status` for Product Development. Each was authored independently; each invented its own walking conventions and output shape; shared primitives (role detection, scope walking, output caching) were re-derived three times. The pattern is general enough to be a first-class capability, and a graduated capability with extension points prevents the next observability tool from being a fourth ad-hoc instance.

The split from `tooling` is deliberate. `tooling` governs *how* a command is wired into the adopter's interface; observability governs *what* is measured and rendered. Conflating them would make every metric family carry tooling-specific concerns (Claude Code path conventions, agent/hook distinctions). Separating them lets the metric families be defined once, then surfaced through any interface an adopter chooses.

## Adoption

Adopters activate `observability` by:

1. Adding a `capabilities.observability` entry to their `.open-org-spec/config.yaml` manifest with `status: active` and an `extension:` path pointing to `.open-org-spec/extensions/observability/spec.md`.
2. Writing the adopter-wide extension at that path, declaring output base path, role-header additions, scope tree, and any threshold values.
3. For each observability tool they adopt, declaring `capabilities.observability.tool_extensions.<tool-name>` in the manifest, pointing at `.open-org-spec/extensions/observability/<tool>/spec.md`.
4. Writing each tool extension with adopter-specific defaults.
5. Wiring a relay at their LLM interface's command directory for each adopted tool.

Worked example: an adopter writes the capability extension at `.open-org-spec/extensions/observability/spec.md`, a first tool extension at `.open-org-spec/extensions/observability/owner-health/spec.md`, a relay at their command directory (e.g. `.claude/commands/owner-health.md`), all declared in `.open-org-spec/config.yaml`.

*(An `oos:adopt-observability` command that scaffolds the manifest entry, the extension files, and the relays is deferred until a second adopter instance.)*

## Reporting

Contributed to the weekly report when this capability is `status: active` in the adopter manifest. The agent-metrics tool reads this section to determine what metrics to compute and render for this capability.

**Section title:** `Observability`

**Data sources:**
- Invocation log — entries for `owner-health`, `inbox-health`, `decision-health`, `contributor-activity`, and `spec-activity` for the past 7 days (run count, `catalogue_assisted` field, timestamps)
- Observability output files — generation timestamps from each tool's output file header (e.g. `governance/observability/owner-health.md`)

**Metrics:**
| Metric | Source | Computation |
|---|---|---|
| Run count (per tool) | Invocation log | Count of entries for that tool in the 7-day window |
| Catalogue-assisted % (per tool) | Invocation log | Fraction of entries for that tool with `catalogue_assisted: true` |
| Last run timestamp (per tool) | Invocation log or output file header | Most recent entry timestamp for that tool |

**Render:** Per-tool table, one row per observability tool that has at least one invocation log entry in the period:

```
| Tool | Runs | Catalogue-assisted % | Last run |
|---|---|---|---|
| /owner-health | N | N% | YYYY-MM-DD |
| /inbox-health | N | N% | YYYY-MM-DD |
| /decision-health | N | N% | YYYY-MM-DD |
| /contributor-activity | N | N% | YYYY-MM-DD |
| /spec-activity | N | N% | YYYY-MM-DD |
```

Tools with no invocation log entries in the period are listed with `—` in all columns.
