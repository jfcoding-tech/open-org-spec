# Proposal: people catalogue

## Intent

Extend the `people` capability with a machine-generated catalogue artefact — `people.yaml` — that aggregates every named person across all `people.md` files in the adoption into a single indexed file. Each entry carries the person's name, scope, scope path, and the feedback inbox path for their primary scope. Agents that need to resolve a person's scope (for routing, ownership lookup, or escalation) read this one file instead of scanning every `people.md` in the repo.

## Rationale

**Agents that route to people currently have to walk the whole repo.** The `risk-at-scope` escalation contract requires routing to the risk owner's scope `feedback.md`. The `adhere-to` spec requires routing conformance gaps to the file's declared owner. Any agent that needs to answer "where does this person's feedback go?" currently has no choice but to scan every `people.md` file in the adoption — an expensive full-repo walk on every run.

**The full-repo walk is fragile, not just slow.** People move between scopes. A person's scope in one `people.md` may disagree with another's, or the latest `people.md` may not yet be committed. An agent reading `people.md` files sequentially can make a routing decision based on stale data and never know it. There is no single authoritative answer to "what is this person's primary scope?" without reading every file and resolving conflicts manually.

**The catalogue pattern already works for other record types.** The `risk-at-scope` capability generates a `risks.yaml` catalogue aggregated from all `risks/` folders. Tools read that one file instead of walking every `risks/` directory. The same pattern applies to decision records. The people catalogue is the same pattern applied to people records — one generated file, authoritative at catalogue-generation time, consumed by all agents that need it.

**A people catalogue makes the organisation's structure queryable without repo traversal.** A tool that needs to answer "who is the Lead of the Customer Lifecycle cluster?" or "what feedback inbox does Howard Tunnicliffe use?" should not have to walk the repo. The catalogue answers both questions with a single file read. This is not just a performance optimisation — it is the difference between agents that can be run cheaply on demand and agents that require substantial context windows to operate correctly.

**It closes a second gap: stale scope assignments surface as catalogue drift.** When the catalogue is regenerated and a person appears in two scopes with conflicting function assignments, the generation step surfaces the conflict rather than silently using whichever file was read last. This makes the `people.md` maintenance obligation visible — stale entries become observable gaps, not hidden misrouting.

**Validated by a concrete failure.** The Busuu risk scanner routed programme-level risk escalations to the governance owner (Javier Fernandez) instead of to the risk owners (Gino, Howard, Collette, Samuel), because the routing table for programme risks defaulted to `governance/feedback.md`. The correct behaviour — route to each owner's scope feedback.md — required a people lookup that the scanner had no efficient way to perform. A people catalogue would have made the correct routing a single file read.

## Delta

Extension to the `people` capability: a new catalogue artefact and a catalogue generation tool.

### Catalogue artefact — `people.yaml`

A machine-generated YAML file at `<adopter-defined-path>/people.yaml` (default: `governance/catalogue/people.yaml`). Generated by the people catalogue agent; never edited by hand. Declared in the adoption manifest's `people` capability entry.

**Schema per entry:**

```yaml
people:
  - name: <full name as recorded in HR>
    primary_scope: <slug of the scope where this person holds their highest-authority function>
    primary_scope_path: <relative path to the scope root from the repo root>
    feedback_inbox: <relative path to the scope's feedback.md>
    function: <function from the people capability's closed vocabulary — Owner | Lead | Driver | Approver | Liaison | Contributor | Member>
    scopes:
      - scope: <slug>
        scope_path: <path>
        function: <function>
        feedback_inbox: <path>
```

**Primary scope resolution.** When a person appears in multiple `people.md` files, `primary_scope` is the scope where they hold the highest-authority function: Owner > Lead > Driver > Approver > Liaison > Contributor > Member. If tied, the scope at the lower depth in the repo tree takes precedence (closer to root = higher scope). The `scopes` array lists every scope the person appears in.

**Generation:** The catalogue agent walks every `people.md` file in the adoption, aggregates records by `name`, resolves primary scope per the authority order above, and writes `people.yaml`. The generated file includes a `generated:` timestamp and a `source_files:` list of every `people.md` it read.

**Conflicts:** If the same person appears in two scopes with the same authority level (e.g. Lead in two different clusters), the agent writes a `conflict: true` flag on the entry and logs it to `governance/observability/spec-health/agent-warnings.md`. The routing tools fall back to `governance/feedback.md` for conflicted entries until the conflict is resolved.

### People catalogue agent

A new command (`/catalogue-people` or as a step within the existing `/catalogue` agent) that generates `people.yaml`. Runs on the same cadence as the risk and decision catalogues.

**Steps:**

1. Walk every `people.md` in the adoption (excluding `closed/`, `_template/`, `context/`).
2. For each `people.md`, extract the Lead table and Working Group table per the `people` capability schema.
3. Aggregate by person name. Resolve primary scope per the authority order.
4. Flag conflicts. Write conflict entries to the warnings file.
5. Write `people.yaml` with `generated:` timestamp and `source_files:` list.
6. Commit: `chore: people catalogue — YYYY-MM-DD`.

### Routing contract for agents

Agents that need to resolve a person's feedback inbox — risk scanner, conformance agent, adhere-to, any future routing-dependent tool — follow this contract:

1. Read `governance/catalogue/people.yaml` (or the adopter-configured path).
2. Look up the person by `name`.
3. Use `primary_scope`'s `feedback_inbox` as the routing target.
4. If the person is not in the catalogue, fall back to a full `people.md` scan (same as today) and log a `[catalogue-miss]` warning.
5. If the catalogue is stale (older than 25 hours), log a `[catalogue-stale]` warning and proceed with the scan fallback.

This contract is declarative — agents do not re-implement the routing logic; they follow the catalogue.

## Acceptance scenarios

### Agent resolves feedback inbox without repo traversal

Given a `people.yaml` catalogue that is current (generated within 25 hours)
When the risk scanner needs to route an escalation for a risk owned by Howard Tunnicliffe
Then it reads `people.yaml`, finds Howard's `feedback_inbox`, and writes the entry there
And it does not open any `people.md` file

### Stale catalogue falls back gracefully

Given a `people.yaml` catalogue older than 25 hours
When an agent attempts to resolve a person's feedback inbox
Then it logs a `[catalogue-stale]` warning and falls back to scanning `people.md` files directly
And the routing still succeeds — the fallback is slower, not broken

### Person in multiple scopes — primary scope resolved by authority

Given a person listed as Lead in `clusters/product-development/people.md` and as Contributor in `projects/foo/people.md`
When the catalogue is generated
Then `primary_scope` is `product-development` (Lead outranks Contributor)
And the `scopes` array lists both entries

### Conflict detected and surfaced

Given a person listed as Lead in two different cluster `people.md` files
When the catalogue is generated
Then the entry carries `conflict: true`
And a warning is written to `governance/observability/spec-health/agent-warnings.md`
And routing tools fall back to `governance/feedback.md` for that person until the conflict is resolved

### Person not in catalogue — fallback without silent failure

Given a person named in a risk record whose name does not appear in `people.yaml`
When the risk scanner attempts to route their escalation
Then it logs a `[catalogue-miss]` warning
And falls back to scanning `people.md` files directly
And if still not found, routes to `governance/feedback.md` with an `[owner-not-found]` note

### Catalogue generation is idempotent

Given a `people.yaml` that was generated yesterday
When the catalogue agent runs again today with no changes to any `people.md`
Then the output is identical except for the `generated:` timestamp
And no spurious changes are committed
