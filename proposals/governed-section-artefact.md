# Proposal: manage the contributor-guide governed section as an artefact

## Intent

Move regeneration of the contributor guide's governed section out of the
LLM-driven `/bump` command and into the install-time artefact mechanism that
`adhere-to` already operates. Today the governed block — the text between
`<!-- oos:governed-start v... -->` and `<!-- oos:governed-end -->` in the
adopter's contributor guide (typically `CLAUDE.md`) — is regenerated by `/bump`
Step 5, which is an LLM instruction that reads `open-org-spec/templates/contributor-guide.md`
at runtime, splices it into the file, and rewrites the sentinel version. This
proposal declares the governed section as an artefact in the `adoption-manifest`
capability's `artefacts` block: a versioned, sentinel-stamped section whose
template lives in the standard and whose installed copy is detected as stale and
reinstalled by `adhere-to` whenever the standard version moves forward. Once the
artefact handles regeneration deterministically, `/bump`'s governed-section step
becomes a thin call into the same artefact path rather than bespoke LLM logic,
and the standalone regeneration behaviour `/bump` carried today is redundant.

## Rationale

Two of the standard's load-bearing principles are violated by the current `/bump`
Step 5, and the artefact mechanism already exists to satisfy both.

**Self-containment — no runtime reads from the standard.** The install-time
expansion pattern is explicit: agents must never read from `open-org-spec/` or
`.open-org-spec/extensions/` at runtime, because everything an installed artefact
needs is expanded into it at install time. `/bump` Step 5 does exactly the
forbidden thing — at the moment a contributor runs the command, it reaches into
`open-org-spec/templates/contributor-guide.md`, reads the governed content live,
and splices it in. That re-couples the regeneration to the presence and exact
layout of the standard directory and to an LLM faithfully following a multi-step
splice instruction. Declaring the governed section as an artefact moves the read
to install time, where `adhere-to` is the only tool licensed to touch the
standard directory, and bakes the expanded result into the adopter's file.

**Model-agnostic, deterministic regeneration.** The governed section is pure
template expansion: substitute `<manifest-owner-name>` and the version, replace
the bytes between two sentinels. There is no reasoning to do. Yet `/bump` Step 5
is phrased as natural-language instructions ("find the sentinel block", "replace
the content between the sentinels", "update the version in the opening sentinel")
that any LLM executes with its own latitude — two models, or two runs, can
produce subtly different results. The artefact mechanism is deterministic by
construction: a `file_contains` check tests the sentinel, a `governed_section`
scaffold replaces a precisely bounded region from a template with declared
variables. Any LLM running `/adhere-to` produces byte-identical output because
the substitution rules are fixed, not interpreted.

**The `adoption-manifest` capability is the correct home, not `tooling`/`adhere-to`.**
The relationship being governed is "content *from* the standard placed *into* the
adopter's contributor guide". The manifest already owns both ends of that
relationship: `contributor_guide` declares the target file, and `owner.name`
supplies the substitution value. `adhere-to` is the *engine* that installs
artefacts, but the artefact *declaration* belongs to the capability that owns the
contract — exactly as the `tooling` capability declares its pre-push hook artefact
and `governance-at-scope` declares its protection hook. Declaring the governed
section under `adoption-manifest` keeps the declaration next to the
`contributor_guide` field it depends on.

**Why a new check/scaffold variant rather than `type: file`.** The contributor
guide is not wholly owned by the standard — the adopter's own routing map, tone,
and organisation-specific rules live *below* `<!-- oos:governed-end -->`, and the
starter skeleton lives there too. A `type: file` artefact would overwrite the
whole file and destroy adopter content. The governed section needs a bounded
replace: detect staleness via the sentinel, then rewrite only the region between
the two markers, leaving everything outside untouched. This is a small, principled
extension to the artefact schema (a `governed_section` type with a
sentinel-delimited replace), not a workaround.

**`/bump` is not deleted, it is simplified.** Version upgrade still needs an
orchestrator — checking out the tag or unpacking the zip, diffing active
capabilities, flagging extension overlap, bumping `standard_version`. What `/bump`
no longer needs is its own bespoke governed-section regeneration: once the
artefact exists, the governed section is updated by the same `adhere-to` sweep
`/bump` already runs across active capabilities. `/bump` Step 5 collapses to "the
`adoption-manifest` adhere-to pass reinstalls the governed section if stale",
removing the only step in `/bump` that read the standard directory at runtime.

## Delta

The delta is authored inside [`./specs-delta/`](./specs-delta/) in a structure that
mirrors the repository root from `specs-delta/` downward.

1. **`specs/adoption-manifest/spec.md`** — add an `artefacts` block (or extend the
   existing one) declaring the governed-section artefact:

   ```yaml
   artefacts:
     - id: governed-section
       type: governed_section
       path: "{{contributor_guide}}"
       template: open-org-spec/templates/governed-section.md
       variables:
         - name: contributor_guide
           source: config.yaml#contributor_guide
         - name: manifest_owner_name
           source: config.yaml#owner.name
         - name: standard_version
           source: config.yaml#standard_version
       sentinels:
         start: '<!-- oos:governed-start v{{standard_version}} -->'
         end: '<!-- oos:governed-end -->'
       check:
         type: file_contains
         value: '<!-- oos:governed-start v{{standard_version}} -->'
       condition:
         type: config_equals
         config_path: capabilities.tooling.status
         equals: active
   ```

   - The `check` uses the version-stamped start sentinel as the staleness sentinel:
     a present-but-older governed block carries `v<old>` and fails the check,
     triggering reinstall — exactly the version-sentinel pattern the artefact
     schema already describes for `file_contains`.
   - The `condition` keeps the artefact aligned with the existing rule that the
     governed section is required only when the `tooling` capability is active
     (per the `contributor_guide` field description).
   - Document the new `type: governed_section` and the `sentinels` field in the
     artefact schema section: a bounded replace that rewrites only the region
     between `sentinels.start` and `sentinels.end`, leaving file content outside
     the sentinels untouched. If the sentinel block is absent, file a
     `[conformance]` entry to the manifest owner rather than guessing where to
     insert it (preserving `/bump` Step 5's current absent-sentinel behaviour).

2. **`templates/governed-section.md`** (new) — the canonical governed content,
   carrying `{{manifest_owner_name}}` and the version-stamped sentinels with
   `{{standard_version}}`. Promoted from the existing
   `templates/contributor-guide.md` body (which is already LLM-agnostic) with the
   sentinel markers and version variable made explicit so the artefact's template
   expansion produces a self-stamping block. `templates/contributor-guide.md` may
   be retired or repointed to this file once the artefact is the source of truth.

3. **`specs/adoption-manifest/bump.md`** — replace Step 5 ("Regenerate the
   governed section") with a pointer: the `adoption-manifest` adhere-to pass run
   during the version sweep reinstalls the governed-section artefact when the
   sentinel version is stale. Remove the runtime read of
   `templates/contributor-guide.md` from `/bump`. Keep the absent-sentinel
   `[conformance]`-entry behaviour as the artefact's documented fallback.

## Acceptance scenarios

### Bumping the standard version updates the sentinel automatically

Given an adopter repo with `tooling` active, `standard_version: "0.4.0"`, and a
contributor guide whose governed block opens with `<!-- oos:governed-start v0.4.0 -->`
When the manifest owner upgrades to `0.5.0` and `/adhere-to tooling` (or the
`adhere-to` pass inside `/bump`) processes the `adoption-manifest` artefacts
Then the `governed-section` artefact's `file_contains` check for
`<!-- oos:governed-start v0.5.0 -->` fails against the `v0.4.0` block, the region
between the sentinels is rewritten from `templates/governed-section.md` with
`standard_version` resolved to `0.5.0` and `manifest_owner_name` resolved from the
manifest, and the opening sentinel now reads `<!-- oos:governed-start v0.5.0 -->`.

### Regeneration is deterministic across LLMs

Given the same adopter repo and the same target version
When two different LLM agents each run the `adhere-to` artefact pass over the
`governed-section` artefact
Then both produce byte-identical governed-section content, because the
substitution rules (sentinel match, owner-name and version variable expansion,
bounded replace) are fixed by the artefact declaration and require no model
reasoning.

### Adopter content outside the sentinels is preserved

Given a contributor guide with organisation-specific routing rules and tone
written below `<!-- oos:governed-end -->`
When the `governed-section` artefact reinstalls because the sentinel version is stale
Then only the bytes between `sentinels.start` and `sentinels.end` are replaced and
all adopter content outside the sentinels is left unchanged.

### Current governed section is skipped, not rewritten

Given an adopter on `standard_version: "0.5.0"` whose governed block already opens
with `<!-- oos:governed-start v0.5.0 -->`
When `/adhere-to tooling` processes the artefact
Then the `file_contains` check passes, the artefact is reported conformant, and no
write occurs — matching the artefact mechanism's skip-when-current behaviour.

### `/bump` no longer reads the standard directory at runtime

Given the simplified `/bump`
When the manifest owner runs `/bump v<new>`
Then `/bump` orchestrates the version checkout/unpack, capability diff, extension
overlap flagging, and `standard_version` update, and the governed section is
regenerated solely by the `adoption-manifest` artefact during the `adhere-to`
sweep — `/bump` itself performs no read of `templates/contributor-guide.md` or any
other file under `open-org-spec/` for the purpose of regeneration.
