# Proposal: scope registry capability

## Intent

Add a `scope-registry` capability that declares all active scopes in an adoption as a machine-generated catalogue — `scopes.yaml`. Each entry carries the scope's structural type, slug, path, feedback inbox, and lead. Artefacts that need to declare which scope they belong to reference a scope by `<type>/<slug>` (e.g. `cluster/product-development`, `function/revenue`, `project/agentic-coach-phase-3`). Agents resolve that reference to a feedback inbox via a single catalogue read.

## Rationale

**The standard defines structural types but has no way to reference a specific scope instance.** The vocabulary of structural types — cluster, function, project, module — exists across multiple capability specs. What is missing is a canonical way for an artefact to say "I belong to *this specific* cluster" or "this risk relates to *this specific* function." Without it, every reference is either a fragile path string (breaks when folders move) or an implicit inference from file location (breaks when artefacts are cross-cutting or live at the programme level).

**A path string is the wrong reference type.** A risk that declares `scope: clusters/product-development` is coupled to a folder structure that can change. A risk that declares `scope: cluster/product-development` is coupled to a logical scope identity — the cluster named `product-development` — which survives folder renames, structural reorganisations, and migrations. The type/slug pair is the stable identity; the path is a derived property.

**Routing requires resolving type/slug to a feedback inbox.** The `risk-scope-field` proposal (and the conformance agent, and any future artefact routing) needs to answer: "given `scope: function/revenue`, what is the feedback inbox?" That resolution requires knowing that `function/revenue` maps to `functions/revenue/feedback.md` in this adoption. The scope registry provides that mapping as a single file read. Without it, agents either hardcode adopter-specific paths (wrong — not generic) or walk the repo to discover them (slow, fragile).

**The adoption manifest is not the right home for scope instances.** The manifest declares which capabilities are active — governance policy. Scope instances are operational content: which clusters, functions, and projects exist in this adoption right now. The manifest is a governance artefact owned by one person and not intended as a queryable registry. Separating them keeps the manifest stable and small, while the scope registry evolves as the adoption grows.

**The scope registry is the instance-level complement to the manifest's type-level vocabulary.** The manifest says "the `cluster` structural type is active." The scope registry says "the active clusters are: product-development, customer-acquisition-growth, customer-lifecycle." The two layers together give a complete picture: the types and the instances.

**Validated by a concrete chain of failures.** Programme-level risks were routed to the governance owner because the scanner could not determine which scope's feedback inbox to target. The `risk-scope-field` proposal provides the declaration; the scope registry provides the resolution. Both are required to make risk routing correct.

## Pattern

### Scope reference format

A scope reference is a two-part string: `<type>/<slug>`. The type comes from the closed vocabulary below; the slug is the folder name of the scope instance.

**Closed type vocabulary:**

| Type | Meaning | Example slug |
|---|---|---|
| `cluster` | A line-of-business cluster | `product-development` |
| `function` | A cross-cutting function | `revenue` |
| `project` | A time-boxed initiative | `agentic-coach-phase-3` |
| `module` | A shared-services or infrastructure module | `ai-factory` |
| `programme` | The repo root — cross-cutting risks and decisions that belong to no single scope | *(no slug — use `programme` alone)* |

The `programme` type has no slug: a reference to `programme` means "this artefact belongs to the entire adoption, not to any one scope." It is the fallback for cross-cutting artefacts.

### Catalogue artefact — `scopes.yaml`

A machine-generated YAML file at `governance/catalogue/scopes.yaml` (adopter-configurable). Generated by the scope registry agent; never edited by hand.

**Schema:**

```yaml
generated: YYYY-MM-DDTHH:MMZ
scopes:
  - type: cluster
    slug: product-development
    path: clusters/product-development
    feedback_inbox: clusters/product-development/feedback.md
    lead: Yaiza Temprado
    status: active
  - type: function
    slug: revenue
    path: functions/revenue
    feedback_inbox: functions/revenue/feedback.md
    lead: Howard Tunnicliffe
    status: active
  - type: project
    slug: agentic-coach-phase-3
    path: projects/agentic-coach-phase-3
    feedback_inbox: projects/agentic-coach-phase-3/feedback.md
    lead: TBD
    status: active
  - type: programme
    slug: programme
    path: .
    feedback_inbox: governance/feedback.md
    lead: <manifest owner>
    status: active
```

Fields per entry:

| Field | Source |
|---|---|
| `type` | Structural type — inferred from folder location |
| `slug` | Folder name of the scope |
| `path` | Relative path from repo root to the scope folder |
| `feedback_inbox` | Relative path to the scope's `feedback.md` |
| `lead` | The Lead declared in the scope's `people.md` lead table; `TBD` if absent |
| `status` | `active` | `closed` — inferred from the scope's spec `status:` frontmatter |

### Scope discovery

The scope registry agent discovers scopes by walking the structural folders declared in the adoption manifest's scope tree (or, if no scope tree is declared, by applying heuristics based on known structural types):

- **Clusters** — every immediate subdirectory of `clusters/` (excluding `governance/`, `context/`, `_template/`, `closed/`)
- **Functions** — every immediate subdirectory of `functions/` (excluding `_template/`, `closed/`)
- **Projects** — every immediate subdirectory of `projects/` (excluding `_template/`, `closed/`)
- **Modules** — folders that are neither clusters nor functions nor projects, declared in the manifest or matching known module patterns (`ai-factory/`, `cloudops/`)
- **Programme** — always present; one entry per adoption at the repo root

Closed scopes (projects with `status: closed` in their spec, or in a `closed/` subfolder) are included with `status: closed` but are not routing targets — agents skip closed scopes when resolving references.

### Resolution contract for agents

Any agent that needs to resolve a scope reference:

1. Read `governance/catalogue/scopes.yaml`.
2. Look up by `type` + `slug`.
3. Use the entry's `feedback_inbox` as the routing target.
4. If the reference is not in the catalogue, log a `[scope-not-found]` warning and fall back to `governance/feedback.md`.
5. If the catalogue is stale (older than 25 hours), log a `[catalogue-stale]` warning and fall back to walking the repo directly.

### Impact on `risk-scope-field`

The `risk-scope-field` proposal's `scope` field format changes from a path string to a type/slug reference:

```yaml
# Before (path string — fragile)
scope: clusters/product-development

# After (type/slug — stable)
scope: cluster/product-development
```

Validation by `/adhere-to risk-at-scope` checks that the declared `scope` value resolves to an entry in `governance/catalogue/scopes.yaml`. An unresolvable scope reference is a `high` severity gap.

### Impact on `people-catalogue`

The `people-catalogue` proposal's `scopes` array entries use the same `type/slug` format for scope references, resolved via this catalogue rather than path strings.

## What is not prescribed

- **Whether the scope registry is the only way to discover scopes.** Agents may still walk the repo directly as a fallback. The catalogue is the fast path, not the only path.
- **The specific folder structure for each type.** This is adopter-specific, declared via the manifest or the scope tree extension. The scope registry discovers whatever structure the adopter has.
- **Whether every scope has a `feedback.md`.** Scopes without a feedback inbox are recorded in the catalogue with `feedback_inbox: null`. Agents that need to route to them fall back to the nearest parent scope's inbox.

## Acceptance scenarios

### Agent resolves scope reference without repo traversal

Given `governance/catalogue/scopes.yaml` containing an entry for `type: function, slug: revenue`
When the risk scanner encounters a risk with `scope: function/revenue`
Then it reads the catalogue, finds `feedback_inbox: functions/revenue/feedback.md`, and routes there
And it does not walk any folder

### Unresolvable scope reference surfaces as high-severity gap

Given a risk with `scope: cluster/nonexistent`
When `/adhere-to risk-at-scope` runs
Then a `high` severity gap is reported: "scope reference `cluster/nonexistent` not found in scope registry"

### Programme scope routes to governance inbox

Given a risk with `scope: programme`
When the scanner evaluates it
Then it routes to `governance/feedback.md` addressed to the risk's declared owner

### Scope registry includes closed projects without routing to them

Given a project `projects/closed/busuu-mcp/` with `status: closed`
When the scope registry is generated
Then the entry appears in `scopes.yaml` with `status: closed`
And agents skip this entry when resolving routing targets

### Folder rename does not break scope references

Given a risk with `scope: function/revenue`
And the adopter renames `functions/revenue/` to `functions/revenue-operations/` and updates the scope slug in `functions/revenue-operations/README.md`
When the scope registry is regenerated
Then the catalogue reflects the new path
And the risk record's `scope: function/revenue` no longer resolves — surfacing a `[scope-not-found]` warning that prompts the adopter to update the risk record's scope slug to `function/revenue-operations`
